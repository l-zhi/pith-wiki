# Roadmap 不锁版本号、不承诺时间表

**状态**：accepted（2026-05-22）

## 背景

v0.1 时期的 [docs/roadmap.md](../roadmap.md) 是传统 OSS 风格：v0.2 / v0.3 / v1.0 / v2.0 各自带时间估算（~2 周 / ~3 周 / ~2 个月 / ~6 个月）+ 任务清单 + 用户故事。

到 2026-05 实际状态：原计划的 v0.2 完成 ~40%、v0.3 完成 ~60%、v1.0 完成 ~30%、v2.0 完成 0%，但同时还交付了大量**完全不在原计划里**的功能（持久化队列、watcher、多 provider、bigram 中文检索、`/digest`、自动 transcript 等）。

继续维护版本号锁定的时间表对 solo dev 是高风险负担：跳一次票 OSS 信任掉 50%，但 solo dev 跳票几乎必然。

## 决定

开源时把 roadmap.md 重写成三栏结构，**不锁版本号、不承诺时间**：

```
## Likely next      ← 短期可能进 0.4 / 0.5 的项；按 issue +1 数排优先级
## Maybe someday    ← 中长期方向；等真实信号触发
## 明确不做         ← Anti-roadmap，避免重复 issue
```

每条 Likely / Maybe 都关联到 GitHub issue。优先级由 issue 上的 reaction count 与讨论质量驱动，**不由作者主观计划驱动**。

## 为什么

1. **诚实**：solo dev 无法持续兑现时间承诺。承诺即翻车
2. **拉社区进决策**：rec_count 驱动优先级 = 早期贡献者有真实参与感
3. **匹配项目定位**：[PRD §1.3](../PRD.md) 明确说"不是产品、不是企业级"。工具没有 OKR
4. **保留实验灵活性**：哪天作者突然想试 embedding 不必先开 ADR 调整 roadmap

## 后果

- **看起来不够"专业"**：对习惯 enterprise OSS 风格的读者，没有版本号路线图看起来项目"没在做事"
- **缓解方式**：roadmap.md 开头一段明确说明这是 solo dev 项目 + 决策机制，把姿态摆清楚
- **未来贡献者警示**：不要"好心"在 roadmap 上重新加版本号 + 时间表。除非项目变成多人维护团队，否则保持当前结构
- **可逆性**：将来项目规模变大、多人维护后可以加回结构化的 roadmap；ADR-0002 届时标 superseded
