# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev         # run the REPL via tsx (no build needed)
npm run build       # tsc → dist/, also chmods bin
npm start           # run built CLI from dist/
npm test            # vitest run (one-shot)
npm run test:watch
npm run typecheck   # tsc --noEmit
```

Run a single test: `npx vitest run tests/library.test.ts` (or `-t "<name>"` to filter by test name).

Subcommands during development: prefix with `npm run dev --` instead of `pith-wiki`, e.g. `npm run dev -- list --collection tech`. Stdin piping works (`cat foo.md | npm run dev -- ingest --collection tech`).

An API key for the active provider is required for `ingest` and the REPL; `get` / `list` / `query` work without it. Keys live in `config.json` — either as a provider entry's literal `apiKey`, or in the top-level `secrets` map keyed by the env-var name the provider/skill reads (see Config precedence). **There is no `.env`** — it was removed; `config.json` is the single source.

## Architecture

`bin/pith-wiki.ts` uses commander to dispatch either to subcommands (`src/cli/subcommands.ts`) or the default Ink REPL (`src/cli/App.tsx`). Both paths instantiate the same three services in `src/wiki/` — there is no parallel implementation for the LLM-tool route.

**Three core services** (`src/wiki/`):

- `LibraryService` — file CRUD over `<wikiRoot>/<collection>/<id>.md` (plus arbitrary-depth subpaths). `scanAll` is **recursive** — it walks every non-dotdir under each collection at any depth, so it is NOT "one level only". The `transcriptsDir` (`config.outputDir`, default `<wikiRoot>/output/transcripts/`) is **explicitly skipped** by passing it as `LibraryServiceOptions.ignoredDirs` (excluded from both the scan and the `collectionTreeMtime` freshness calc), so raw REPL transcripts that share the `output` collection's tree root never get indexed — don't rely on the old accident where transcript filenames violated `ID_RE` and got dropped on parse. Forward links live in YAML frontmatter; backlinks are computed lazily into an in-memory `Map<id, {forward, backward}>` and invalidated on any `put`/`delete`. Atomic writes via `.tmp + rename`.
- `HydrationService` — calls DeepSeek in JSON mode (`response_format: json_object`). When `autoLink=true` it injects existing entries' `{id, title, summary}` into the prompt as link candidates. **Cannot be combined with tools** — JSON mode and `tools` are mutually exclusive on the OpenAI-compatible API.
- `ContextAssembler` — no embeddings. Tokenizes via `\W+`, scores entries (`2*title + 2*tags + summary + 0.5*content`), takes top 5 seeds, expands forward links BFS depth=1, and packs to a `maxTokens × 4 chars × 0.7` byte budget. The 0.7 leaves headroom for the rest of the conversation.

**REPL agent loop** (`src/llm/agent.ts`): trusts `tool_calls.length > 0` (not `finish_reason`) to decide whether to recurse; loop cap is 12 iterations (`maxSteps`). If the loop hits the cap while the model still wants to call tools, `send()` does **not** return an empty string — it runs one final `forceFinalAnswer()` request **without** `tools` (so the model must answer from what it gathered) and fires `onAssistantText({final:true})`; if even that is empty it throws `AgentError('model_error')`. Tool calls run serially through a `p-queue(concurrency=1)`. The `AbortController` from the UI is forwarded into the OpenAI client so `Ctrl+C` kills the in-flight HTTP request *and* prevents further tool dispatch. LLM requests time out after `config.requestTimeoutMs` (default 120s; env `PITH_WIKI_TIMEOUT_MS`) instead of the SDK's 10-minute default.

**Tool registry** (`src/tools/`): eleven tools — file: `read_file`, `write_file`, `list_dir`; wiki retrieval: `wiki_query`, `wiki_grep`, `wiki_list`, `wiki_get`, `wiki_read_source`; wiki write: `wiki_ingest`, `wiki_queue_add`, `wiki_queue_status`. Wiki tools are thin wrappers over the same services subcommands use. `wiki_grep` does exact substring/regex search and **by default greps each entry's ORIGINAL source** — `source.cachePath ?? source.value` (the raw `.md` for passthrough notes, the converted `.md` sidecar for PDF/EML/HTML), resolved through `resolveSafePath('read', …)` + `truncatePayload`, so verbatim words survive even when hydration compressed them out of the digest. It falls back to the in-memory `Entry.content` when the source is unreadable (url/inline, binary without a sidecar, out-of-sandbox, missing); each result item's `searched` field says `'source'` or `'content'`. Title/summary/tags are always grepped in-memory. `patterns` is OR-combined (list every surface form of a fixed value like a date in one call) with an optional `regex` mode. Only entries already in the index are searched (failed-ingest files are invisible). It's the exact/full-census complement to `wiki_query`'s fuzzy scored search over the compressed digest. `src/tools/index.ts` ships a hand-rolled `zodToJsonSchema` that only understands `string|number|boolean|array|enum|optional|default|object` — if you add a tool whose params use other zod constructs (unions, records, refinements), extend the converter or the schema will silently degrade to `{}`.

**Skills** (`src/skills/`): installable capability packages discovered from `config.skillDirs` (default dual-location like `soulFile`: `<pithWikiHome>/skills` + `<workspaceRoot>/skills`, project-local last so it wins on name collision). Each skill is a dir with a `SKILL.md` (gray-matter frontmatter `name`/`description`/`type`). Two kinds, both auto-discovered: **prompt skills** (`type: prompt`, default) carry markdown instructions in the body — exposed via a single dynamic `skill` tool (`src/tools/skill.ts`, built by `makeSkillTool(registry)`) whose description bakes in the catalog; the model calls `skill(name)` and the body returns as the tool result (Codex-style progressive disclosure). **Code skills** (`type: tool`, frontmatter `entry: ./x.js`) dynamically `import()` a JS module exporting `ToolDef`(s), merged into the agent via `extraTools`. `SkillRegistry` mirrors `ConverterRegistry`; `buildSkillRegistry()` is **async** (the import) so the REPL/subcommands build it at the call site and pass it through `BuildContextExtras` → `ToolContext.skillRegistry`, exactly like the converter pipeline. Code skills run **unsandboxed in-process**, so `allowCodeSkills` defaults to **false** — code skills are then discovered + listed but never imported (`ToolSkill.loaded=false`). The catalog is baked at Agent construction, so adding a skill needs a REPL restart (same lifecycle as SOUL.md/converters). REPL: `/skill` lists; **each skill is exposed as a dynamic slash command `/<name>`**, so `/<name> <question>` runs it in one line (prompt skill body pinned via `Agent.injectContext`, then the question routed through `handleSubmit`). Built-in commands always win on name collision — `filterCommands(prefix, extra)` drops any dynamic command whose name matches a built-in name/alias, and `handleSlashCommand`'s built-in branches are checked before the dynamic-skill fallback. Skill commands are fed to `InputBox` via `extraCommands` for autocomplete. `/skill <name> <question>` and `/<name>` alone (load + wait) also work. CLI: `pith-wiki skill list|add <path>|remove <name>` (`src/cli/skillCommands.ts`). Env: `PITH_WIKI_SKILLS`, `PITH_WIKI_ALLOW_CODE_SKILLS`. Gotcha: code-skill tool params still pass through the hand-rolled `zodToJsonSchema`, so unions/records degrade to `{}`.

**HTTP-integration skills** (`src/tools/http_request.ts`, ADR-0004 amendment): sibling of run_command for "prompt skill + HTTP gateway" services (e.g. 微信读书 `Tencent/WeChatReading` POSTs to `i.weread.qq.com/api/agent/gateway` with `Authorization: Bearer $WEREAD_API_KEY`). Skill frontmatter declares `http_allow: [{host, auth_env?, auth_header=Authorization, auth_scheme=Bearer}]`; `SkillRegistry.allowedHosts()` is host→rule, and `http_request` mounts only when non-empty. Two gates: host whitelist + safety — **https-only**, **auth injected by the tool from `auth_env` so the model never sees/sets the key** (no `headers` param at all; Content-Type controlled by the tool), cross-host redirect to a non-allowlisted host is rejected (stops the key following a 302 off-host), `config.httpTimeoutMs` (default 30s) abort, response `truncatePayload`'d. **Declaration is the authorization — NO per-request approval** (unlike run_command, which still approves each binary): a host declared in an installed skill's `http_allow` is greenlit at install time, so the agent calls it with no runtime prompt. http_request's narrow surface (host allowlist + https + auth injection + cross-host redirect reject) makes per-call approval low-value and harmful to the "install and use" flow. There is no `approvedHosts`/`requestNetworkApproval`/`kind:'net'` — those were removed. Params are url/method/body/content_type/timeout_ms (all zodToJsonSchema-safe). This makes "install an HTTP-gateway skill + set one env key" a generic capability — a pith-wiki-flavored weread skill just declares `http_allow: [{host: i.weread.qq.com, auth_env: WEREAD_API_KEY}]`, zero wrapper script. Outbound HTTP bodies are also covered by the security filter (PR #42, client layer).

**CLI-integration skills** (`src/tools/run_command.ts`, ADR-0004): skills can wrap external CLIs (weread, lark-cli) so the agent actually runs them. A skill declares `commands: [bin, …]` (a binary whitelist) and optional `requires: [{bin, install}]` in its SKILL.md frontmatter. `SkillRegistry.allowedCommands()` is the union of all installed skills' `commands`; `run_command` is mounted **only when that set is non-empty** (same conditional-mount pattern as `makeSkillTool`). Three gates: (1) whitelist — `command` must be in `allowedCommands()`; (2) approval — each new binary needs `requestCommandApproval` (REPL only; `ApprovalRequest.kind='exec'`; `a` adds to `ToolContext.approvedCommands` per-binary). Non-interactive paths (subcommands/queue worker) have no approval channel → `run_command` refuses outright (executing is a notch more dangerous than writing, so unlike write_file there is no subcommand bypass); (3) sandbox — `spawn(shell:false, cwd:workspaceRoot, stdin:ignore)` so pipes/redirection/injection can't happen and interactive commands fail fast instead of hanging; timeout (`config.commandTimeoutMs`, default 60s) SIGTERM→SIGKILL; stdout+stderr merged and `truncatePayload`'d; exit code returned. **Bundled (built-in) skills** (`src/skills/bundled.ts`): a set of optional skills shipped inside the npm package at `<packageRoot>/bundled-skills/<name>/SKILL.md` (in `package.json` `files`; located via `import.meta.url` — the module sits at `src|dist/skills/`, so **two levels up is the package root**). They are **NOT** in `config.skillDirs`, so `buildSkillRegistry` never discovers them — zero context cost until installed (no catalog entry, no tool mount, no slash command). `skill add <name>` resolves a bundled name (after git, before local-path) and copies it into `skillDirs[0]` — **zero download, offline**. `listBundledSkills(baseDir?)` / `resolveBundledSkill(name, baseDir?)` take an injectable baseDir for tests. `skill list` (CLI + REPL) shows an "Available to install (bundled)" group for bundled skills not yet installed. First bundled skill: `weread` (微信读书, declares `http_allow: i.weread.qq.com` + `WEREAD_API_KEY`) — user flow is `skill add weread` + set `WEREAD_API_KEY` in `config.json`'s `secrets` map (desktop UI does this via `setSkillEnv`), no clone.

Install core lives in `src/skills/install.ts` (`installSkillFromSource` / `removeSkillByName` / `checkRequirements` — structured returns, no console coupling; `InstallResult.source` is `'git'|'bundled'|'local'`), shared by the CLI subcommands and the REPL. `pith-wiki skill add` (and REPL `/skill add <source> [--force]`) accepts a local dir, a git URL, or a GitHub `owner/repo` short name (`git clone --depth 1` to tmp, validate, copy, strip `.git`); installing a skill with `commands` prints an authorization notice, and `requires` bins are `command -v`-probed with install hints (never auto-installed — supply-chain risk stays an explicit user action). **REPL `/skill add` / `/skill remove` hot-reload**: they re-run `buildSkillRegistry` + `setSkillRegistry`, which rebuilds the agent useMemo so the new skill's catalog/slash-command/run_command mount take effect immediately — at the cost of resetting the conversation history (same semantics as `/provider` switch). `removeSkillByName` refuses names that `path.join` out of a skillDir (no `../` escape). Outbound CLI output is covered by the security filter (it sits in the client layer, so tool results are masked too). **Code skills (`type: tool` + `entry`) are explicitly NOT implemented** — the in-process-JS approach was rejected in favor of this declarative model; ignore older AGENTS.md text describing them.

**Scheduled tasks** (`src/schedule/`, docs/PRD-schedule.md): a task = "at a time, run a `input` string through the agent for one turn, persisting the result as a reopenable session". Core is UI-free (`cron.ts` hand-rolled 5-field cron — offline, zero-dep, mirrors the hand-rolled `zodToJsonSchema` ethos; `store.ts` = sync mutate + atomic write, **no lockfile** since the only writer is the single-process desktop engine; `service.ts` = CRUD + `computeDue` catch-up decisions). Schedule is `{kind:'once', at} | {kind:'cron', expr, tz}`. Two surfaces over the same `ScheduleService`: agent tools `schedule_add/list/update/delete/status` (`src/tools/schedule.ts` — the once|cron union is **flattened** to `kind/at/cron/tz` params because the hand-rolled `zodToJsonSchema` degrades unions to `{}`; mounted only when `ToolContext.scheduleService` is injected, i.e. desktop only) and the desktop UI. **Trigger host = the desktop engine only** (`desktop/src/engine/scheduler.ts`): a 30s tick runs `computeDue → markTick`, executes due tasks serially through a `p-queue(concurrency=1)` (same-task-in-flight → skipped), and `SessionManager.runScheduled` opens a fresh session per fire. **Fires only while the app is open + catches up missed fires on launch** (no OS-level background in v1). catch-up: cron collapses N missed fires to one `catchUp` run, once fires late, `catchUp=false` records `skipped`; failures are NOT retried. `nextFire`/`fireTimesBetween` feed the renderer's calendar (future fires + past runs overlaid). State at `~/.pith-wiki/schedule/state.json` (`config.scheduleStatePath`); cron eval is **system-local time** in v1 (tz stored as metadata).

**Sandbox** (`src/tools/safety.ts`): every path resolved through `read_file` / `write_file` / `list_dir` must land under `workspaceRoot` ∪ `wikiRoot`. Both are passed through `realpathSync` to neutralize symlinks (notably macOS `/var` → `/private/var`). Write targets in not-yet-existing directories use `realPathClimbing` — walks upward to the first existing ancestor, realpaths it, then re-attaches the missing tail. Symlinks pointing outside the sandbox are rejected post-realpath.

**Approval flow**: in REPL mode, every new write path triggers an approval prompt. Answers: `y` (this path only), `a` (whole session — added to `approvedWritePaths`), `n` (refuse). Subcommands bypass this (no UI).

**Security filter** (`src/security/`): outbound LLM filter, **on by default** (`securityEnabled`; opt-out via `PITH_WIKI_SECURITY=0` or config `false`). On first use, if no `security.json` exists at any layer, `createClient` writes a starter template to `~/.pith-wiki/security.json` (all five presets explicit `mask`, empty `rules` — discoverable/editable, never overwrites). `createClient` is the single choke point — it monkey-patches `chat.completions.create` (`wrap.ts`), so Agent / hydrate / runPlan / queue worker are all covered; **never instantiate `new OpenAI` directly in CLI/REPL paths, always go through `createClient`**. Two rule levels: `block` (request refused with `SecurityBlockError`; `Agent.send` splices the whole turn back out of history so the session isn't permanently poisoned) and `mask` (replaced with reversible `[LABEL_N]` placeholders). The `Sanitizer`'s original↔placeholder map lives as long as the client, so re-masking the agent's replayed history is deterministic. Responses are restored in place — `message.content` (JSON-escaped when the request used `response_format: json_object`), `tool_calls[].function.arguments` (always JSON-escaped), `reasoning_content`/`thinking` — so wiki entries land on disk with the *original* values; sensitive data never leaves the machine but local data stays intact. When masking occurred, the wrap layer appends a "preserve placeholders verbatim" note to the request's system message (centralized — agent/hydration prompts need no edits). Rules come from built-in CN-centric PII presets (phone/idCard/bankCard+Luhn/email/apiKey, all default `mask`, individually `off`-able) merged union-style with dual-location `security.json` (`~/.pith-wiki/` + `<workspaceRoot>/`, env `PITH_WIKI_SECURITY_RULES`; preset conflicts resolve to the stricter level: block > mask > off). Bad JSON / unknown keys / invalid regex in rules files fail fast at startup. Placeholders contain `[`/uppercase/`_` so `ID_RE` rejects any that leak into entry ids. Transcripts are deliberately **not** sanitized (local audit trail).

**Config precedence** (`src/config.ts`): CLI flag > env (`PITH_WIKI_*`, plus any var named by a provider's `apiKeyEnv` / skill's `auth_env`) > `~/.pith-wiki/config.json` > built-in defaults. Parsed through zod — invalid config is fail-fast at startup. **Secrets**: `config.json`'s `secrets` map (KEY→plaintext) is loaded into `process.env` at the **start** of `loadConfigFromEnv` (before provider/secret reads), so it is the single persisted source for API keys (replacing the removed `.env`). Two valid key placements, both in `config.json`: a provider entry's literal `apiKey`/`oauthToken` (what `init` and the desktop Settings UI write), **or** `secrets[<NAME>]` where a provider's `apiKeyEnv` / a skill's `http_allow.auth_env` names `<NAME>`. Desktop `setSkillEnv` and `init --api-key` both persist here. Literal `apiKey` still wins over the env-resolved value within a provider entry.

## Conventions worth knowing

- Entry IDs are slugs enforced by `EntrySchema` via `ID_RE` (`src/wiki/types.ts`): either ASCII kebab-case (`a-z 0-9 -`) or CJK (Han / Hiragana / Katakana / Hangul), the two styles joinable with hyphens — no uppercase, spaces, dots, or leading hyphen. Hydration prompt repeats this rule but the schema is the actual gate.
- TS config uses `NodeNext` modules, so all relative imports inside `src/` and `bin/` end in `.js` (not `.ts`). Tests in `tests/` are excluded from the build but vitest resolves them fine.
- `npm run build` writes only `bin/` and `src/` to `dist/`; `tests/` is excluded by `tsconfig.json`.
- `--url` on `ingest` only tags the entry's `source` — it does **not** fetch. Pipe content via `--file` or stdin.
- The wiki layer is `Promise`-light: `LibraryService` is sync (filesystem only); only `HydrationService` and the agent are async.

## Desktop app（@pith/desktop，`desktop/`）

pith 桌面端（Electron）。**实现 UI 前先读 `design/pith-design-system/README.md`**（设计 handoff 规则）。架构见 ADR-0005/0006 与 docs/PRD-desktop-v1.md；领域词汇见 CONTEXT.md。

```bash
cd desktop
npm install        # 独立 node_modules（不与根 workspace 耦合）
npm run dev        # electron-vite dev（HMR）
npm run build      # electron-vite build → out/
npx electron .     # 跑构建产物
npm test           # 三个深模块的 vitest（根 npm test 也会收编这些用例）
npm run typecheck  # tsconfig.node.json + tsconfig.web.json 双侧
```

- **Engine**（`desktop/src/engine/`）= utilityProcess 里的核心宿主：装配共享 LibraryService/SkillRegistry/converters + 每会话一个 Agent + 内置 queue worker；入口 `index.ts` 先装 polyfill（pdfjs legacy 需要 DOMMatrix）再**动态 import** `bootstrap.ts`——ESM 静态提升会让外部依赖先于同模块 polyfill 求值，这个分界不能合并。
- **EngineBridge**（`src/shared/protocol.ts`）：sessionId 事件流 + correlationId 请求-响应；main 是哑管道。审批 = approvalRequest 事件 + approval.answer 请求。
- **SessionStore**（JSONL @ `~/.pith-wiki/sessions/`）只存对话本体；system prompt 由 Agent 配置自持，恢复时经 `Agent.restoreHistory` 重建（该 API 因桌面端加入 core）。
- Engine 通过 `@core/*` 别名直接 import 仓库根 `src/`（electron-vite 把 `.js` 后缀解析回 `.ts`）；@pith/core 物理拆包仍是后续步骤，**engine 只允许 import 核心层 + UI-free 的 dashboardData/queueOps**，不得碰 ink/commander 模块。
- 桌面端 workspace 语义 = 全局单工作区：engine 启动时 chdir 到 `~/.pith-wiki`。
